# Upstream SUB/WAVE v1.9.0 Integration and Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Merge exact upstream SUB/WAVE `v1.9.0` into ObiWave, preserve fork-only behavior and manual-only vulnerability scanning, merge a reviewed green PR, publish immutable `v1.9.0-obiwave.1`, and deploy it successfully to production.

**Architecture:** Work in an isolated integration worktree and create one non-fast-forward merge whose second parent is the exact upstream tag. Compose upstream v1.9 behavior with fork contracts, then use focused tests, full package/browser/container gates, independent review, an exact-head PR merge, and the existing protected Portainer deployment. Release publication must not invoke or depend on vulnerability scanning.

**Tech Stack:** Git, Node.js 22, npm, TypeScript, Zod, React, Next.js, Python 3, Liquidsoap, Docker Buildx, GitHub Actions, GHCR, Portainer, CUDA, Chatterbox, PocketTTS, and Playwright-backed verification.

**Spec:** `docs/superpowers/specs/2026-08-24-upstream-v1.9.0-integration-design.md`

## Global Constraints

- Execute in `.worktrees/integrate-upstream-v1.9.0` on branch `integrate/upstream-v1.9.0`.
- The execution base is exact `origin/develop` containing the approved design and this plan; record its SHA and stop on unexpected drift.
- `v1.8.0` is `bc541fbecb6fe5ce5355cedb52a5cfcad965932f`; `v1.9.0` is `65c840ee9b099a8270cee4e88ab9993b9455c245`; the merge base must be exact v1.8.0.
- Create exactly one upstream integration merge commit whose second parent is exact v1.9.0.
- Preserve upstream behavior and additive/stricter fork behavior. Never accept an ambiguous conflict wholesale.
- Preserve authentication, station isolation, provider-keyed credentials and URLs, Kagi/LiteLLM, strict schemas, queue/voice ownership, analyzer extensions, CPU/CUDA images, immutable identities, Portainer deadlines, health probes, and rollback.
- Vulnerability scanning remains manual-only. Do not add or run a schedule, `workflow_call`, build/release/recovery/finalization/deployment scan, or invoke `scan-images.yml`. Keep its `workflow_dispatch` trigger.
- Browser verification uses the `verify` skill, disposable state, spare ports, dummy Subsonic, and fresh provenance. Never use production configuration, credentials, state, or services for test setup.
- The release is exactly `v1.9.0-obiwave.1`. Never move, overwrite, rebuild, or retag it. Do not create mobile EAS releases.
- Deployment failure restores and verifies the exact prior stack; successful rollback still means deployment failed.
