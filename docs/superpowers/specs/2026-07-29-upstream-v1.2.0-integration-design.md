# Upstream v1.2.0 Integration and Fork Release Design

## Goal

Integrate the exact upstream SUB/WAVE `v1.2.0` release into ObiWave from the
current fork `develop`, preserve intentional fork capabilities, merge the
verified integration through a pull request, and cut and deploy the immutable
fork release `v1.2.0-obiwave.1`.

The completed release must contain all upstream v1.2.0 security, request,
broadcast, Admin, and web-player fixes while retaining these fork contracts:

- strict listener-request matching;
- Kagi Web Search with provider-owned credentials;
- authenticated MP3, Opus, AAC, and FLAC web playback with listener-selected
  format persistence and safe fallback;
- fork-qualified image publication;
- immutable mirroring of the upstream CUDA analyzer image;
- Ark's fail-closed CUDA analyzer configuration;
- Portainer production deployment and verified rollback; and
- the fork's CI, release, and deployment policy.

No fork history is rebased or rewritten. The ten upstream commits between
v1.1.1 and v1.2.0 are not cherry-picked individually.

## Upstream v1.2.0 Scope

Upstream v1.2.0 is authoritative for:

- listener-request injection, flooding, duplicate-pending, acknowledgement,
  requester-name, and spoken-intro guards;
- per-IP and global request limits plus trusted client-IP handling;
- the security and robustness corrections from the upstream deepsec audit;
- atomic broadcast marker writes;
- stem-clip loudness matching;
- the controller's request, listener-auth, client-IP, language-anchor,
  stem-level, and voice-policy tests;
- audio-element remount detection and media-listener reattachment;
- honest stalled/playing state based on media-clock progress;
- listener-visible track timing based on advertised stream buffer depth;
- newest-first Admin booth logs;
- upstream release metadata, changelog, deepsec configuration, and operational
  documentation; and
- timeout protection for every built-in web-search provider.

Cleanly merged upstream paths remain upstream-owned unless a fork contract test
or this design identifies an intentional fork capability that must be composed
with the new implementation.

## Merge Policy

Conflict resolution follows these rules:

1. Accept upstream behavior when it replaces equivalent fork behavior.
2. Preserve only the fork contracts listed in this design.
3. Express retained behavior through the v1.2.0 architecture instead of
   restoring obsolete pre-v1 modules or interfaces.
4. Treat upstream security validation and rate limits as minimum requirements;
   fork behavior may compose with them but never bypass or weaken them.
5. Regenerate derived files from their canonical sources.
6. Avoid unrelated cleanup, refactoring, dependency upgrades, and product
   changes.

A dry merge predicts seven textual conflicts.

### `controller/src/routes/request.ts`

Use upstream v1.2.0's request route as the security baseline. Preserve the
fork's strict-request behavior by composing `request-strict.ts` after upstream
has cleaned and screened listener input.

The combined route must:

- apply upstream request text and requester-name cleaning before any value is
  stored, logged, sent to an LLM, displayed, or spoken;
- enforce upstream per-IP, global, and one-pending-request limits;
- retain upstream acknowledgement and intro guards;
- retain upstream guard diagnostics without exposing unsafe raw input through
  public responses;
- evaluate strict-request targets from the cleaned request;
- prevent the conversational agent from satisfying a specific strict target
  with an unrelated track;
- keep deterministic strict candidate selection and the fork's honest
  not-found response; and
- preserve upstream queue, duplicate, and rate-limit commit semantics on every
  terminal path.

Both upstream request-hardening tests and the fork's strict-request tests are
acceptance criteria.

### `controller/src/skills/web-search.ts`

Retain the fork's five-provider architecture and provider-owned credential
resolution for DuckDuckGo, Tavily, Brave, SearXNG, and Kagi.

Apply upstream's bounded `fetchWithTimeout` behavior to DuckDuckGo and Tavily,
while retaining the existing bounded calls for Brave, SearXNG, and Kagi. Kagi
continues to use only its saved `search.apiKeys.kagi` value or `KAGI_API_KEY`
fallback; it never reads `SEARCH_API_KEY` or another provider's saved key.

Provider-aware cache keys, recency handling, parser safety, entity decoding,
secret redaction, diagnostics, and live Admin probes remain unchanged except
where an upstream timeout or error contract is stricter.

### Web player conflicts

The four conflicting player paths are:

```text
web/components/player/PlayerCore.tsx
web/components/player/PlayerShell.tsx
web/hooks/usePlayer.ts
web/hooks/useStationFeed.ts
```

The result must combine upstream's remount and timing corrections with the
fork's authenticated multi-format player.

`usePlayer` remains the owner of selected format, browser/platform
capabilities, stored preference, authenticated stream URLs, MP3 fallback,
volume, tune state, and reconnect state. Its callback ref must:

- update `audioRef.current` whenever the shell mounts, unmounts, or replaces
  the audio element;
- detach listeners and tear down the replaced element;
- attach media listeners to every newly mounted element;
- use upstream's media-clock progress check before reconnecting;
- treat `stalled` as a network hint rather than proof that playback stopped;
- use `timeupdate` to reconcile a connecting status when audio is moving; and
- retain format-specific failure attribution and MP3 fallback without erasing
  the listener's stored preference.

The public callback may keep the fork's `audioElementRef` name rather than
upstream's `attachAudio` name because it already represents the same stable
callback-ref contract. `PlayerShell` must attach that callback, not the plain
object ref.

`useStationFeed` must stop using `buffered.end - currentTime` as the listener
delay. It must retain the fork's per-format stream metadata and use the
advertised buffer duration for the currently selected format through
`bufferSecondsForFormat`. This keeps v1.2.0's corrected timing model without
regressing optional-format timing.

`PlayerCore` keeps stream capability discovery and the selected-format
dependency needed by `useStationFeed`, but removes the obsolete measured-lag
dependency. Audio format controls, station authentication, media-session
metadata, signal state, and context update boundaries remain intact.

### `CLAUDE.md`

Combine upstream v1.2.0's request-guard, atomic marker-write, stem-level, and
listener-timing guidance with the fork's Kagi, strict-request, authenticated
multi-format playback, CUDA mirror, Portainer, and fork-release contracts.
Remove superseded measured-buffer guidance.

## Pull Request and Merge

Push `integrate/upstream-v1.2.0` to `origin` and open a pull request into
`develop` titled:

```text
chore: integrate upstream SUB/WAVE v1.2.0
```

The PR body summarizes the upstream release, the seven semantic conflict
resolutions, retained fork contracts, verification evidence, and release
follow-up.

Merge only after all required checks pass and the PR head still matches the
verified local commit. Use the repository's normal merge-commit policy; do not
squash away the exact upstream merge ancestry. Confirm `origin/develop`
contains `v1.2.0` after the PR merges.

No PR from `develop` to `main` is part of this fork release. Fork image releases
are cut directly from the verified `develop` target by the dedicated workflow.

## Fork Release and Deployment

The release tag is exactly:

```text
v1.2.0-obiwave.1
```

Before dispatching the release workflow:

- confirm the GitHub release tag does not already exist;
- confirm none of the ten fork GHCR repositories already contains that exact
  tag;
- confirm upstream CUDA image
  `ghcr.io/perminder-klair/subwave-analyzer-cuda:1.2.0` exists and is
  inspectable;
- confirm `v1.2.0` is an ancestor of the selected `develop` commit; and
- record the exact merged `origin/develop` SHA that will be released.

Dispatch:

```bash
gh workflow run cut-fork-release.yml \
  --repo ObiWanCanOweMe/obiwave \
  -f version=1.2.0 \
  -f revision=1 \
  -f target=develop
```

The cut workflow must create the GitHub release at the recorded `develop` SHA.
The resulting tag triggers the existing immutable publication pipeline.

Monitor the complete release to a terminal state:

1. validate the fork-qualified tag;
2. repeat the complete CI release gate;
3. prove all ten destination image tags are absent;
4. mirror the upstream CUDA analyzer with digest equality;
5. build and publish the nine fork-built images;
6. scan every authenticated private image;
7. deploy the exact release through the protected production environment;
8. verify the public health endpoint; and
9. verify a non-empty authenticated or public MP3 stream, according to the
   configured production secret.

The production deployment must pin every image to
`v1.2.0-obiwave.1`; mutable tags are forbidden.

## Failure and Rollback Policy

- Any conflict whose ownership cannot be established stops the integration for
  review.
- Any upstream security test failure blocks the PR; no guard or limit is
  weakened to make the merge pass.
- Any fork contract regression blocks the PR; obsolete fork code is not
  restored as a shortcut.
- A failed PR check is diagnosed and fixed on the integration branch before
  merge.
- A release preflight failure stops before tag creation or image publication
  whenever possible.
- If immutable publication partially succeeds, do not overwrite or reuse the
  partial tag. Follow the documented full-matrix cleanup procedure before a
  controlled rerun.
- If production deployment or verification fails, the deployment client must
  restore the saved Portainer stack and environment and verify the rollback.
- A workflow that ends after a verified rollback is still a failed deployment;
  report the release as published but not deployed.
- If rollback verification also fails, report the production incident and stop
  for operator intervention without exposing secrets or Portainer response
  bodies.

## Completion Criteria

The task is complete only when:

- the integration PR is merged into `develop`;
- `develop` contains the exact upstream `v1.2.0` tag in its ancestry;
- all required PR and release checks pass;
- GitHub release `v1.2.0-obiwave.1` targets the verified merged commit;
- all ten immutable fork image tags exist;
- the CUDA mirror digest equals the upstream v1.2.0 CUDA image digest;
- Portainer reports the exact fork release tag;
- the production health and MP3 stream probes pass; and
- no rollback or unresolved production incident remains.
