# Upstream SUB/WAVE v1.6.0 Integration Design

## Objective

Integrate the exact upstream SUB/WAVE `v1.6.0` release into ObiWave's current `develop` branch, preserve fork-only operational and security contracts, verify the composed result, and open a reviewed pull request. This phase ends at the open, green pull request. It does not merge the pull request, create `v1.6.0-obiwave.1`, publish images, or deploy production.

## Exact Starting Identities

- Fork base: `origin/develop` at `0e57fa1af15cdbfa944f005a7df2320ea5124f98`.
- Upstream release: tag `v1.6.0` at `c9b4a24d363f44b002722750e6c0b6a7845cae7a`.
- Upstream baseline already integrated: tag `v1.5.0` at `8c01e979ebeea5c5ed6cac6658b5da14322b9d6d`.
- `v1.5.0` must remain an ancestor of both the fork base and `v1.6.0`.
- The integration branch is `integrate/upstream-v1.6.0` in the linked worktree `.worktrees/integrate-upstream-v1.6.0`.

The upstream delta contains nine commits and changes 118 paths. Its functional themes are library exploration and recency, a more agentic provider-aware LLM layer, per-file picker tools and authored instructions, Zod-backed webhook validation and forms, and an admin scroll-area fix.

## Integration Strategy

Create one non-fast-forward merge of the exact `v1.6.0` tag into the fork base. The resulting merge commit must have the pre-merge integration branch as its first parent and `c9b4a24d363f44b002722750e6c0b6a7845cae7a` as its second parent.

This is preferable to cherry-picking because it proves that the complete upstream release is present and keeps future merge-base calculations truthful. It is preferable to rebasing or synthesizing a tree because the fork's published ancestry and recovery history must not be rewritten.

Conflict decisions follow three rules:

1. Upstream wins when it supersedes the same behavior with a compatible replacement.
2. Fork-only behavior remains when upstream has no equivalent.
3. Independent overlapping behavior is composed and protected with a focused regression test.

No ambiguous conflict is resolved by accepting an entire side wholesale.

## Predicted Conflict Resolution

The merge preview identifies six conflicted paths.

### Consolidated CI

Upstream modifies `.github/workflows/lint.yml`, which ObiWave intentionally replaced with `.github/workflows/ci.yml`. Keep the upstream workflow deleted. Port its new schema-mirror generation check and controller/web Zod-version parity check into ObiWave's existing controller quality job. Preserve all fork quality packages, analyzer test provisioning, deployment-contract tests, Docker image smoke jobs, action versions, permissions, and concurrency behavior.

### Settings Normalization

Compose `controller/src/settings/normalize.ts` rather than selecting either side. Preserve fork fallback-TTS normalization, including engine, voice, cloud-provider, gain, and speed rules. Adopt upstream's shared schema-backed webhook identity and normalization helpers so malformed stored data is repaired leniently while strict save-path validation remains aligned with the generated web schema. Existing settings files must boot without manual edits.

### Web Dependencies

Merge `web/package.json` so upstream's React Hook Form, Zod resolver, shadcn field, and scroll-area dependencies coexist with fork dependencies. Regenerate `web/package-lock.json` from the composed manifest with the repository's pinned package-manager workflow. Controller and web must declare the same runtime Zod range.

### Architecture Documentation

Reconcile `controller/CLAUDE.md` and `web/CLAUDE.md`. Add upstream's agent-loop, picker-tool, schema-generation, form, accessibility, and scroll-area contracts while retaining fork guidance for provider-owned credentials, fallback TTS, private-station authentication, listener behavior, security gates, and deployment topology.

Upstream's deletion of obsolete shared Superpowers plans/specs is accepted. ObiWave-only integration, remediation, recovery, security, and deployment records remain because they are fork-only history.

## Behavioral Composition

### Library Exploration and Recency

Adopt upstream's airing-memory store, wider picker exploration sources, and scaled recency. Preserve these existing constraints around the expanded candidate pool:

- blocklist rules, including seasonal, tag, genre, and show scope;
- show mood, genre, era, energy, vocal, duration, and playlist filters;
- library likes and operator mutations;
- analyzer vector and audio-mood behavior;
- station-archive exclusion;
- queue locking and committed-pick behavior.

Database schema changes must migrate through normal library initialization. Existing play history remains readable, and new airing observations must not mutate production state during development tests.

### Agentic LLM Layer

Adopt upstream's provider-aware agent loop shape, authored instruction files, and per-file picker-tool registry. Preserve fork contracts for provider capability translation, provider-owned base URLs and credentials, primary/fallback reachability, deadlines and retries, structured output validation, picker locking, and safe text recovery.

Tool scope must keep blocklists, show constraints, recency, and request identity intact. A provider that requires the forced-tool object path must continue to receive it through the capability descriptor rather than call-site provider branches.

### Webhook Schema and Form Boundary

Controller schemas are the source of truth. `controller/scripts/gen-schemas.ts` produces the committed web mirror at `web/lib/schemas.generated.ts`; CI regenerates it and fails on drift. Controller and web use the same Zod range.

The webhook form adopts upstream's React Hook Form and shadcn field foundation. Existing webhook IDs and redacted `authHeader` values must survive edit/save cycles. Client validation, server validation, field-error mapping, field-array identity, and accessible labels/descriptions must remain consistent. Invalid hand-edited stored values are repaired or dropped on load rather than preventing controller boot.

### Fork Operational Contracts

The merge must not weaken:

- immutable release and exact-image publication rules;
- Trivy acceptance and recovery-manifest policy;
- one-time v1.3 and v1.5 recovery safeguards;
- Portainer validation, rollback, and analyzer readiness checks;
- listener-auth edge isolation and private-station credentials;
- provider secret redaction and provider-specific URL ownership;
- playback format hydration and stream-format gating;
- fallback-TTS voice behavior.

## Error and State Safety

All runtime verification uses the integration worktree, disposable controller state, and non-production ports. It must not write to the live station's `state/`, restart production services, publish images, mutate tags, or dispatch deployment workflows.

Stop the integration when any of these occurs:

- the upstream tag identity or ancestry is not exact;
- the actual conflict set differs materially from the preview without explanation;
- a conflict cannot be resolved confidently under the three composition rules;
- an existing settings or library database migration fails;
- schema generation or Zod parity drifts;
- a focused or full-suite regression remains unexplained;
- independent review retains a Critical or Important finding;
- GitHub checks do not pass on the exact reviewed head.

## Verification Strategy

### Baseline

Install locked dependencies in the isolated worktree and run the current full local CI equivalent before merging. Record any pre-existing failure rather than attributing it to v1.6.0.

### Focused Red-Green Gates

For every composed behavior missing after the raw merge, add or adapt a focused test, observe the relevant failure, implement the minimum correction, and rerun it. The focused gate includes:

- upstream airing-memory, auto-pool, recency, picker-registry, picker-show-source, discovery-step, authored-instruction, schema-generation, schema, and validation-middleware tests;
- fork fallback-TTS, provider credential, settings security, picker-lock, listener-auth, playback hydration, recovery-manifest, workflow-contract, Trivy-policy, and Portainer tests;
- web form typechecking and production build with generated schema drift checks.

### Full Local Gate

Run controller lint and its complete scripted suite; web lint, focused browserless state/provider tests, and production build; MCP lint; CLI typecheck; native-app lint/typecheck and stream/auth tests; release, security, deployment, and workflow contract tests; `git diff --check`; generated theme and schema drift checks; and affected controller/web image smoke builds.

Exercise the controller and admin webhook/settings surfaces from the worktree with disposable state. Validate that the controller boots, schema-backed webhook requests report usable field errors, the admin form loads and edits rows, and no request reaches production.

### Review and Pull Request

Obtain an independent whole-branch review on the final local head. Fix all Critical and Important findings and rereview the changed head. Push only after the exact head is verified, then open a pull request from `integrate/upstream-v1.6.0` to `develop` summarizing upstream features, explicit conflict resolutions, behavioral tests, and the absence of release/deployment actions.

All GitHub checks must pass. The pull request remains unmerged pending explicit user approval.

## Deliverables

- one exact-tag v1.6.0 merge commit on `integrate/upstream-v1.6.0`;
- composed conflict resolutions and focused regression coverage;
- a complete local verification record;
- an independently reviewed, pushed branch;
- one open, green integration pull request to `develop`;
- no `v1.6.0-obiwave.*` tag, release, image, workflow dispatch, merge, or deployment.
