# Finalize v1.6.0-obiwave.4 Design

## Context

The `v1.6.0-obiwave.4` publication first failed while downloading the Piper
voice for the controller image. A failed-job rerun resolved that transient
Hugging Face CDN error and published every image. The aggregate vulnerability
gate then failed closed because the release tag was not present in
`PINNED_CUDA_IMAGE_DIGESTS`.

The mirror job and an independent registry inspection both report the exact
CUDA repository digest as
`sha256:cdf74b46d05a40d453b69541644b4e9e7c587617100a7484a616e358efd3c341`,
the same immutable upstream v1.6.0 artifact already reviewed for `.1`, `.2`,
and `.3`.

## Design

Use the established `.3` recovery pattern rather than moving or rebuilding the
immutable `.4` tag:

1. Add `v1.6.0-obiwave.4` to the release-aware CUDA digest map and extend the
   cross-release policy tests.
2. Record all ten already-published `.4` image repository digests in an
   immutable recovery manifest tied to source commit
   `b96ef42c6a014ecf96964809a42370ad5e6954ea` and the pinned Trivy scanner.
3. Add a manual, release-specific finalizer that verifies every registry
   digest against the manifest, rescans those exact digests, enforces the
   vulnerability policy, reverifies the artifacts, and deploys `.4` through
   the existing protected production environment.

The normal tag-push publisher is not changed. The finalizer cannot accept a
different tag, source commit, image set, scanner, or deployment target.

## Failure handling and safety

- Registry digest drift fails before scanning or deployment.
- Missing or additional images fail manifest validation.
- Critical/High policy findings still block deployment.
- The production job remains downstream of both immutable-artifact validation
  and the aggregate vulnerability gate.
- The existing tag is never moved or overwritten.

## Verification

- Demonstrate RED by extending the supported-release CUDA test to `.4` before
  adding the production pin.
- Run the Trivy policy and workflow-contract test suites.
- Validate the recovery manifest locally against the registry.
- Run repository CI on a PR, merge only when green, then dispatch and monitor
  the `.4` finalizer through deployment health checks.
