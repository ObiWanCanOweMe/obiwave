# v1.3.0-obiwave.2 Release Recovery Design

## Context

`v1.3.0-obiwave.2` was cut once from reviewed merge commit
`41c8a329670f99c3b440a468adbb9fe2d900a4fe`. Nine first-party images and the
exact upstream CUDA mirror were published successfully. Deployment did not run
because all ten scan jobs used `aquasecurity/trivy-action` with Trivy `v0.67.2`.
That Trivy version has a Git tag but no GitHub Release assets, so the action's
installer deterministically returned HTTP 404 before producing JSON or SARIF.
The aggregate policy failed closed and Portainer remained unchanged.

The released Git tag, GitHub release, and image tags are immutable. Recovery
must scan and deploy those existing artifacts without rebuilding, retagging,
or weakening the accepted-risk policy.

## Selected approach

Fix the reusable scanner to run the already-reviewed Trivy 0.67.2 container by
immutable digest, then add a one-release recovery workflow anchored to an
exact checked-in manifest for `v1.3.0-obiwave.2`.

This is preferred over two alternatives:

1. A manual workstation scan followed by a manual Portainer update would be
   difficult to audit and would bypass the protected GitHub environment.
2. Abandoning `.2` and cutting `.3` would preserve automation simplicity, but
   would leave the requested, already-published `.2` release undeployed.

## Scanner repair

Replace both installer-based Trivy action invocations in the reusable scan
workflow with direct `docker run` calls against a central checked-in scanner
configuration. Normal and recovery scans both consume that configuration. The
recovery manifest independently records the expected scanner digest, and its
validator requires the two records to agree before scanning; this prevents a
later general scanner update from silently changing the approved `.2` recovery.

Each matrix job will:

1. authenticate to GHCR;
2. retain the existing production-child-command probe for controller and AIO;
3. resolve and compare the release image's registry manifest digest when a
   recovery manifest is supplied;
4. run Trivy JSON and SARIF scans against the digest-qualified release image;
5. write the existing status schema with scanner version `0.67.2` and the
   canonical tag reference;
6. upload JSON/status and SARIF through the existing artifact channels.

Scanner startup, image pull, database download, JSON generation, or malformed
output failures remain reportable status failures. The aggregate policy keeps
requiring all ten JSON/status pairs and zero unaccepted Critical/High
occurrences. SARIF upload remains an observability channel and cannot satisfy
or bypass the JSON policy gate.

## Recovery workflow

Add a manual workflow dedicated to `v1.3.0-obiwave.2`; it accepts no mutable
release identity inputs. It runs from the default branch after the recovery PR
merges and has three ordered stages:

1. **Validate:** load the checked-in recovery manifest, prove tag/release source
   identity, verify the exact ten registry manifest digests, and prove the
   pinned scanner container reports version 0.67.2.
2. **Scan and enforce:** call the repaired reusable ten-image scanner with the
   fixed release tag and recovery manifest. The unchanged acceptance file and
   `trivy-policy.mjs` decide the gate.
3. **Deploy:** only after validation and policy success, enter the existing
   protected `production` environment and invoke
   `scripts/deploy/portainer-release.mjs` with the existing environment
   variables and secrets.

The deployment retains the existing target verification, timeout handling,
snapshot, and verified rollback behavior. The recovery workflow does not
contain a policy waiver, alternate acceptance file, force flag, image build,
tag push, release mutation, or direct Portainer API implementation.

## Tests and review gates

Tests must be behavioral or structural at the workflow boundary:

- recovery-manifest parser tests reject source, tag, scanner, image-set, and
  digest drift;
- registry-verifier tests cover exact matches, missing/extra images, malformed
  output, and child-process failure without contacting production;
- workflow contract tests require the pinned Trivy container and forbid the
  broken installer action;
- recovery workflow contract tests require validation and policy dependencies,
  the protected production environment, existing deploy script, exact fixed
  release identity, and absence of build/tag/waiver paths;
- existing vulnerability-policy, release, Portainer, and workflow suites remain
  green;
- an independent reviewer must approve the exact PR head and GitHub Actions must
  pass before merge.

After merge, dispatch the recovery workflow exactly once. Independently verify
all ten registry digests, policy output, deployment image tags and restart
counts, public health and now-playing metadata, both listener-auth 404s, exact
65,536-byte MP3 range delivery with `audio/mpeg`, audible mean volume above
`-50 dB`, and recent analyzer/controller/broadcast logs. Report whether target
deployment succeeded or the existing rollback path restored and verified the
previous release.

## Non-goals

- No rebuild or replacement of any `v1.3.0-obiwave.2` artifact.
- No modification of `v1.3.0-obiwave.1`.
- No integration of upstream v1.4.
- No accepted-risk expansion or expiry change.
- No generalized release-resume system beyond repairing the reusable scanner
  and the one exact `.2` recovery workflow.
