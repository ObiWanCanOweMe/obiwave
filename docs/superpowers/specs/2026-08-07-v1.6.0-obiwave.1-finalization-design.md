# v1.6.0-obiwave.1 Identity-Only Finalization Design

## Status and decision

The partial-publication recovery run `31191879092` successfully published the five missing images, sealed all ten release-image digests, and scanned every digest-qualified image with the pinned Trivy 0.67.2 scanner. Its aggregate policy gate then failed on 19 newly surfaced occurrences of `CVE-2026-8458`, so the protected production deployment did not run.

The operator approved a time-bounded acceptance for this finding and an identity-only finalization path. The finalization must never build, republish, retag, or overwrite an image. It must validate and scan the exact ten digests already sealed by the failed recovery run, and it may deploy only after every validation and policy gate succeeds.

## Security finding and risk decision

`CVE-2026-8458` affects libcurl connection reuse when an application uses HTTP Negotiate authentication with different service names. The upstream curl advisory rates the issue Low, states that it requires the same hostname, port, credentials, and a live pooled connection, and explicitly says that the curl command-line tool is unaffected. SUB/WAVE does not configure HTTP Negotiate, `CURLOPT_SERVICE_NAME`, or `CURLOPT_PROXY_SERVICE_NAME`; its checked-in curl usage is command-line health checking and ordinary HTTP fetching.

Trivy nevertheless classifies the Debian package findings as High and reports no fixed Debian package version for the exact installed packages. Debian currently lists bookworm and trixie as vulnerable without a DSA. The policy must continue to fail closed unless the precise occurrences are explicitly reviewed.

Add seven exact-scope acceptance records for the 19 occurrences:

1. `curl@8.14.1-2+deb13u4` in `subwave-broadcast`, `subwave-aio`, and `subwave-aio-heavy`: `unreachable`.
2. `libcurl3t64-gnutls@8.14.1-2+deb13u4` in the same three images: `unreachable`.
3. `libcurl4t64@8.14.1-2+deb13u4` in the same three images: `unreachable`.
4. `curl@7.88.1-10+deb12u15` in `subwave-controller`, `subwave-tts-heavy`, `subwave-analyzer`, and `subwave-analyzer-heavy`: `unreachable`.
5. `libcurl4@7.88.1-10+deb12u15` in the same four images: `unreachable`.
6. `curl@7.88.1-10+deb12u15` in `subwave-analyzer-cuda`: `upstream-mirror`.
7. `libcurl4@7.88.1-10+deb12u15` in `subwave-analyzer-cuda`: `upstream-mirror`.

Every record will use:

- vulnerability: `CVE-2026-8458`;
- owner: `SUB/WAVE maintainers`;
- approval date: `2026-08-07`;
- expiry date: `2026-11-05`, exactly the policy's 90-day maximum;
- tracking: the upstream curl advisory at `https://curl.se/docs/CVE-2026-8458.html`;
- a justification specific to the disposition and runtime scope.

The `unreachable` justification will capture the advisory's trigger conditions, the curl CLI exclusion, and SUB/WAVE's lack of Negotiate/service-name configuration. The CUDA justification will preserve the existing `upstream-mirror` rule: that image is an exact immutable upstream mirror bound to the reviewed release digest and is not rebuilt or mutated by SUB/WAVE.

No general CVE waiver, version wildcard, image wildcard, indefinite expiry, severity downgrade, or scanner bypass is permitted.

## Finalization workflow

Add `.github/workflows/finalize-v1.6.0-obiwave.1.yml`, following the established identity-only v1.3/v1.5 recovery pattern.

The workflow will be manual-only (`workflow_dispatch`) with a one-release concurrency group and no cancellation of an in-flight run. It will have three strictly ordered stages:

1. **Validate immutable artifacts.** Check out the dispatch SHA, authenticate read-only to GHCR, and run `recovery-manifest.mjs verify-all` against the committed full manifest and pinned scanner configuration. This validates the GitHub tag/release/source identity and all ten registry digests before scanning.
2. **Enforce vulnerability policy.** Call the existing reusable `scan-images.yml` workflow with release tag `v1.6.0-obiwave.1` and the committed full recovery manifest. Every image is resolved to its manifest digest and scanned with the pinned scanner. The aggregate policy must accept all current Critical/High findings, reject stale or orphaned acceptances, and succeed before deployment becomes eligible.
3. **Deploy production.** Depend on both validation and vulnerability policy, use the protected `production` environment and the shared `subwave-production` concurrency group, and invoke the existing bounded Portainer release deployer with the literal release tag. Existing health, now-playing, listener-auth routing, stream content-type, byte-count, and audio-volume verification remain the deployment gate and rollback boundary.

The workflow contains no build matrix, image push permission, package write permission, tag operation, release creation, or fallback path around the scanner. A failed validation, scanner, aggregate policy, environment approval, deployment, or health check leaves the workflow failed and must not be blindly rerun until its exact state is understood.

## Tests and review

Implementation will be test-driven:

- Extend the checked-in acceptance tests so the seven records, their exact image/package/version scopes, dispositions, dates, tracking URL, and justifications are contractual.
- Add workflow-contract tests for the new finalizer: manual-only trigger, literal release identity, full-manifest validation, digest-based reusable scan call, protected production environment, required dependencies, bounded deploy command, and absence of build/push paths.
- Extend recovery-manifest tests so the committed v1.6.0 full manifest is accepted only at its exact reviewed identity and rejects mutated tag, source, scanner, namespace, order, count, and digest fields.
- Reproduce the failed aggregate policy locally using the downloaded run artifacts: it must fail before the new acceptances and pass afterward with all current findings accepted and no orphaned records.
- Run the focused recovery/security/workflow suites, then the repository's relevant full CI gates before pushing a PR.
- Request independent code review before merge. After merge, dispatch the finalization workflow once and monitor it through validation, all ten scans, policy aggregation, protected deployment, and fresh production probes.

## Alternatives considered

### 1. Identity-only finalization with time-bounded acceptance — selected

This preserves the already-published immutable `.1` artifacts, records the reviewed risk precisely, reuses the existing fail-closed scanner and deploy gates, and avoids any tag mutation.

### 2. Wait for Debian packages and cut `.2`

This avoids accepting the current Debian packages but delays the requested release and abandons deployment of the already-sealed `.1` image set. It remains the fallback if the accepted risk changes or the exact trigger becomes reachable.

### 3. Rebuild patched images as `.2` immediately

This could carry a manually backported curl patch, but it creates a new release and a larger supply-chain change than the narrow runtime exposure warrants. The immutable `.1` tags still could not be overwritten. This is not selected.

## Completion criteria

The work is complete only when:

- the seven time-bounded records match exactly the 19 reviewed findings;
- the full ten-image v1.6.0 manifest is committed and independently validated against GHCR and GitHub release identity;
- the finalization PR passes CI and is reviewed and merged;
- the finalization workflow succeeds through all ten digest scans and the aggregate policy;
- the protected Portainer deployment succeeds and fresh production probes meet every release-health contract;
- the original outage-stalled publication run and failed partial-recovery run remain preserved as audit evidence;
- no image, tag, release, or existing digest is overwritten.
