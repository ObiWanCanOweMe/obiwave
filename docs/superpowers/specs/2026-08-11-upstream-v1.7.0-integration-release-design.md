# Upstream SUB/WAVE v1.7.0 Integration and Release Design

## Objective

Integrate the exact upstream SUB/WAVE `v1.7.0` release into ObiWave's current
`develop` branch, preserve fork-only runtime, security, and deployment
contracts, merge a reviewed green pull request, publish immutable fork release
`v1.7.0-obiwave.1`, and deploy that release to Ark through the protected
Portainer production workflow.

Completion requires a healthy production API and authenticated live-stream
probe. A safe rollback is not completion; if publication or deployment fails,
recovery must continue through the repository's immutable recovery controls.

## Exact Release Identity and Scope

- Upstream release: tag `v1.7.0` at
  `816fb6fd13d622988ad870e7b1ef55155ba314c2`.
- Upstream baseline already integrated: tag `v1.6.0` at
  `c9b4a24d363f44b002722750e6c0b6a7845cae7a`.
- Initial fork head: `origin/develop` at
  `578739b8712c69d244457b413a4b0b5be017fc41`; execution must re-fetch and
  either prove this identity or update the recorded starting identity before
  merging.
- Integration branch: `integrate/upstream-v1.7.0` in linked worktree
  `.worktrees/integrate-upstream-v1.7.0`.
- Fork release: `v1.7.0-obiwave.1`, created from the exact reviewed merge
  result through `.github/workflows/cut-fork-release.yml`.
- Production target: Ark, through the existing protected Portainer workflow.
- Native iOS and Android store releases are out of scope because upstream
  `v1.7.0` contains no native-app delta.

The upstream delta contains 27 commits and changes 257 paths. Its main themes
are shared Zod schemas and React Hook Form across settings and admin editors,
TanStack Query library state, robust `fieldErrors`, lenient legacy-settings
migration, backup preservation of LLM keys, and persistence of
`stream.bufferSeconds`.

## Integration Architecture

Create one non-fast-forward merge of exact tag `v1.7.0` into the pinned fork
head. The merge commit must have the pre-merge integration branch as its first
parent and `816fb6fd13d622988ad870e7b1ef55155ba314c2` as its second parent. This
keeps both published histories truthful and makes the complete upstream release
an explicit ancestor for future integrations.

Conflict decisions follow three rules:

1. Upstream wins when it replaces the same behavior with a compatible new
   schema, component boundary, or runtime implementation.
2. Fork-only behavior remains when upstream has no equivalent.
3. Independent overlapping behavior is composed and protected by focused
   regression coverage.

No ambiguous conflict may be resolved by selecting an entire side wholesale.
Auto-merged files on fork contract boundaries receive the same review as
explicit conflicts.

The merge preview against the initial fork head identifies 25 conflicted paths.
They fall into four policy groups.

### Settings and Schemas

Adopt upstream's per-key Zod registries, strict save validation, lenient legacy
migration, structured `fieldErrors`, backup-key preservation, and
`stream.bufferSeconds` persistence. Retain fork provider-owned URLs and
credentials, exact-origin discovery, secret redaction, fallback TTS, LiteLLM
behavior, embedding retry controls, and normalization rules. Existing settings
and backup files must boot or restore without losing keys or requiring manual
edits.

### Admin Forms and Library State

Adopt upstream React Hook Form and TanStack Query boundaries, including stable
field-array identity and appended-row errors. Compose fork library mutations,
show constraints, playlist behavior, provider controls, and admin navigation
into the new components. Generated schema mirrors remain controller-owned and
must fail CI on drift.

### Player and Runtime

Adopt upstream request/form fixes and runtime library replacements while
retaining private-station authentication, station credentials, four-format
playback, format hydration, provider behavior, request hardening, queue safety,
and listener-facing state semantics.

### Containers, Operations, and Documentation

Retain Ark topology, Caddy authentication boundaries, Icecast secrets,
analyzer behavior, CUDA mirroring, immutable release rules, Trivy policy,
Portainer rollback, and deployment health probes. Accept compatible upstream
container/runtime fixes and update architecture documentation to describe the
composed result.

## Verification Design

All local runtime checks use the linked worktree, disposable state, and
non-production ports. They must not read or write the live station state,
restart production services, publish images, move tags, or dispatch deployment
workflows.

Establish a locked-dependency baseline before the merge. Record pre-existing
warnings or failures rather than attributing them to `v1.7.0`. For every
missing composed behavior found after the raw merge, first add or adapt a
focused test, observe the relevant failure, implement the minimum correction,
and rerun it.

Focused gates cover:

- settings registries, strict and lenient migration, backup key retention,
  `fieldErrors`, schema generation, and stream-buffer persistence;
- stations, shows, skills, playlists, imaging, onboarding, requests, schedule,
  personas, blocklists, library forms, appended rows, and TanStack Query state;
- provider credentials and discovery, LiteLLM, fallback TTS, embedding retries,
  private-station authentication, stream format hydration, and player behavior;
- Caddy, Icecast, controller and AIO startup, release identities, CUDA mirror,
  Trivy policy, Portainer rollback, and GitHub workflow topology.

The full local gate includes controller, web, MCP, CLI, and native-app lint,
typechecking, scripted suites, generated-file drift checks, the web production
build, release/security/deployment contract tests, affected container smoke
builds, isolated controller/admin browser verification, `git diff --check`, and
a clean tracked tree.

Obtain whole-branch review on the final local head. Fix every Critical or
Important finding and re-review the changed head. Push the integration branch,
open a pull request to `develop`, wait for required checks, and merge only the
exact reviewed green head.

## Release and Deployment Flow

After the integration PR merges, dispatch `.github/workflows/cut-fork-release.yml`
with `version=1.7.0`, `revision=1`, and `target` set to the exact merged
`develop` commit. The workflow must prove upstream-tag ancestry and absence of
the fork tag before creating GitHub release `v1.7.0-obiwave.1`.

The tag-triggered publication pipeline remains authoritative:

1. Validate the immutable fork tag and rerun repository CI.
2. Prove all ten exact image tags are absent.
3. Build nine first-party images and mirror the exact upstream CUDA analyzer.
4. Record immutable repository digests.
5. Scan all ten images with the pinned Trivy scanner.
6. Enforce the aggregate Critical/High vulnerability policy.
7. Enter the protected `production` environment.
8. Update Ark through Portainer and verify the API health and authenticated
   stream endpoints.

The ten release images are `subwave-caddy`, `subwave-broadcast`,
`subwave-controller`, `subwave-web`, `subwave-aio`, `subwave-aio-heavy`,
`subwave-tts-heavy`, `subwave-analyzer`, `subwave-analyzer-heavy`, and
`subwave-analyzer-cuda`.

## Failure Handling and Safety

Stop before merge or release if any exact identity or ancestry check fails, the
actual conflict set materially differs without explanation, a composition
decision is ambiguous, required local or GitHub checks remain red, or review
retains a Critical or Important finding.

Stop before production if an image is missing, an image tag already exists,
the CUDA mirror identity differs from policy, an immutable digest cannot be
proved, or the vulnerability gate rejects an artifact.

Once `v1.7.0-obiwave.1` exists, never move or overwrite it and never rebuild a
different artifact under the same identity. A partial publication uses the
repository's sealed immutable recovery process. A failed production probe
invokes automatic rollback to the previous version and verifies that rollback.
If rollback itself is unverified, report an operator incident immediately and
do not claim completion.

## Completion Evidence

The final handoff records:

- integration PR URL, reviewed head, merge commit, and both merge parents;
- proof that upstream `v1.7.0` is an ancestor of `develop`;
- local verification and GitHub check results;
- GitHub release and immutable `v1.7.0-obiwave.1` tag identity;
- publication, mirror, scan, and aggregate policy workflow results;
- all ten published image identities;
- Portainer deployment result, previous and target versions, API health, and
  authenticated stream-probe result;
- any non-blocking warnings or recovery actions.
