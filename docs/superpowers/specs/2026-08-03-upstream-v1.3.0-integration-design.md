# Upstream v1.3.0 Integration and Fork Release Design

## Goal

Integrate the exact upstream SUB/WAVE `v1.3.0` release into ObiWave from the
current fork `develop`, preserve intentional fork capabilities, merge the
verified integration through a pull request, and cut and deploy the immutable
fork release `v1.3.0-obiwave.1`.

The completed release must contain every upstream v1.3.0 feature and fix while
retaining these fork contracts:

- strict listener-request matching;
- LiteLLM and provider-owned Kagi Web Search settings, probes, and credentials;
- authenticated MP3, Opus, AAC, and FLAC playback with listener-selected format
  persistence and safe fallback;
- Ark's Caddy edge-authentication and fixed network contract;
- fork-qualified immutable image publication;
- exact mirroring of the upstream CUDA analyzer image;
- Ark's fail-closed CUDA analyzer configuration;
- Portainer production deployment with verified rollback; and
- the fork's CI, release, and deployment policy.

## Upstream v1.3.0 Scope

Upstream v1.3.0 is authoritative for:

- liked-track visibility and operator heart controls in the Admin library;
- never-play visibility and one-click undo in the Admin library;
- a 15-value show music-filter cap and a 2,000-character show-topic brief cap;
- Fish Audio `s2.1-pro` cloud TTS support;
- Admin voice-clone import;
- `sourceTrackId` in `track.play` webhook payloads;
- analyzer idle unloading, worker recycling, cold-embedding retries, and health
  residency reporting;
- fresh native-app stream reloads after rapid buffering churn;
- Icecast idle-pause hysteresis when a single listener poll fails;
- air-time-correct spoken clocks and non-stacking station idents;
- improved musical-similarity signal, artist-recency memory, and seed-tool
  fallback behavior;
- bounded archive retention with the keep-forever upgrade guard;
- stem-cache enforcement and sweep-shortfall reporting;
- updated coded prompts and AI SDK provider versions;
- the upstream newsprint contrast refresh and Admin editor overflow fix; and
- upstream release metadata, documentation, and generated deployment assets.

Cleanly merged upstream paths remain upstream-owned unless a fork contract test
or this design identifies intentional behavior that must be composed with the
new implementation.

## Merge Policy

Conflict resolution follows these rules:

1. Accept upstream behavior when it replaces equivalent fork behavior.
2. Preserve only the fork contracts listed in this design.
3. Express retained behavior through the v1.3.0 architecture instead of
   restoring removed modules or interfaces.
4. Do not weaken upstream limits, security validation, idle controls, cache
   budgets, or secret-handling behavior.
5. Regenerate derived files from canonical sources.
6. Avoid unrelated refactoring, dependency changes, and product changes.

A dry merge predicts 20 conflict paths, grouped below.

### Environment and generated CLI assets

The conflicts are:

```text
.env.example
cli/src/assets.generated.ts
```

`.env.example` must include upstream's Fish Audio and analyzer idle-lifecycle
configuration while retaining the fork's provider-specific Kagi credential,
CUDA analyzer, and mirror guidance. Generic `SEARCH_API_KEY` must not become a
fallback for Kagi.

`cli/src/assets.generated.ts` is generated output. Resolve `.env.example`, the
Compose files, Caddy, and deployment inputs first; run the canonical CLI asset
generator; commit its output; and prove a second generation produces no diff.
Do not hand-merge generated fragments.

### Analyzer, embedding, and broadcast guards

The conflicts are:

```text
controller/scripts/analyze-quiet.test.ts
controller/src/music/tag-library/embed.ts
```

Adopt upstream's failed-Icecast-poll idle-pause test and the v1.3 analyzer
idle-recycle expectations. Preserve the fork's fail-closed CUDA deployment
policy outside the portable analyzer implementation: upstream's CPU behavior
remains valid for standard images, while Ark's production CUDA service must
still refuse to run without a positive CUDA probe.

Adopt upstream's musical-similarity embedding path, including cold-embed retry
and empty-seed recovery. Retain existing fork provider isolation and timeout
behavior; embedding or search failures must degrade through the documented
fallbacks without borrowing another provider's credentials.

2. Confirm the merge commit's second parent is exact tag commit `c1ce23df`.
3. Regenerate CLI assets and theme tokens, then prove a second generation is

4. Run controller lint, type checking, and the complete controller test suite.
5. Run web lint, every CI-listed focused contract test, and a production build.
6. Run app lint, type checking, and all CI-listed app contract tests, with no
   new warnings relative to the baseline.
7. Run CLI and MCP type checking.
8. Run the complete deployment-contract suite.
9. Validate and render the checked-in Portainer Compose manifest.
10. Inspect the final diff for accidental loss of strict requests, LiteLLM,
    Kagi, authenticated stream selection, edge auth, CUDA mirroring, or
    rollback protection.

The pull request must pass the complete GitHub Actions matrix, including image
smoke builds, before merge.

## Pull Request and Merge

Push `integrate/upstream-v1.3.0` to `origin` and open a pull request into
`develop` titled:

```text
chore: integrate upstream SUB/WAVE v1.3.0
```

The PR body summarizes upstream v1.3.0, the semantic conflict resolutions,
retained fork contracts, verification evidence, and the planned fork release.

Merge only after every required check passes and the PR head still matches the
verified local commit. Use a merge commit; do not squash away exact upstream
ancestry. Confirm the merged `origin/develop` contains `v1.3.0`.

No `develop`-to-`main` PR is part of this fork release. Fork releases are cut
directly from the verified `develop` target by the dedicated workflow.

## Fork Release and Deployment

The release tag is exactly:

```text
v1.3.0-obiwave.1
```

Before dispatching the release workflow:

- confirm the GitHub release and Git tag do not already exist;
- prove none of the ten fork GHCR repositories contains that exact tag;
- confirm upstream image
  `ghcr.io/perminder-klair/subwave-analyzer-cuda:1.3.0` exists and is
  inspectable;
- confirm `v1.3.0` is an ancestor of the selected `develop` commit;
- record the exact merged `origin/develop` SHA; and
- confirm Portainer endpoint 14's edge agent is connected before any production
  deployment begins.

Dispatch:

```bash
gh workflow run cut-fork-release.yml \
  --repo ObiWanCanOweMe/obiwave \
  -f version=1.3.0 \
  -f revision=1 \
  -f target=develop
```

The cut workflow must create the GitHub release at the recorded `develop` SHA.
The tag then triggers the immutable publication pipeline, which must:

1. validate the fork-qualified tag;
2. repeat the complete CI release gate;
3. prove all ten destination tags are absent;
4. mirror the exact upstream CUDA analyzer with digest equality;
5. build and publish the nine fork-built images;
6. scan every deployment-critical image;
7. deploy the exact tag through the protected Portainer environment; and
8. verify public health and MP3 stream bytes.

After the workflow succeeds, independently verify every running production
image is pinned to `v1.3.0-obiwave.1`, controller and broadcast are healthy,
restart counts remain zero, now-playing metadata is populated, the MP3 stream
has the expected content type, and an ffmpeg audio-level probe reports audible
content above the `-50 dB` silence threshold.

## Failure and Rollback Policy

- Any conflict whose ownership cannot be established stops for review.
- Any upstream security, idle-control, secret-isolation, or cache-budget test
  failure blocks the PR; those constraints are not weakened to make tests pass.
- Any fork contract regression blocks the PR; obsolete fork code is not
  restored as a shortcut.
- A failed PR check is diagnosed and fixed on the integration branch before
  merge.
- A release preflight failure stops before tag creation or publication whenever
  possible.
- Immutable tags are never overwritten or reused after partial publication.
- If the Portainer edge agent is disconnected, restore and verify the control
  tunnel before dispatching or retrying deployment.
- If production deployment fails, the deployment client must restore the saved
  Portainer stack and verify the rollback.
- A verified rollback still means the new release is not deployed; report that
  state accurately.
- If rollback verification fails, stop for operator intervention without
  exposing secrets or Portainer response bodies.

## Completion Criteria

The task is complete only when:

- the integration PR is merged into `develop`;
- `develop` contains exact upstream tag commit `c1ce23df` in its ancestry;
- all required PR and release checks pass;
- GitHub release `v1.3.0-obiwave.1` targets the verified merged commit;
- all ten immutable fork image tags exist;
- the CUDA mirror digest equals the upstream v1.3.0 CUDA image digest;
- every production service uses the target fork tag with no restart loop;
- public health, metadata, MP3 byte-flow, and non-silent audio probes pass; and
- no rollback or unresolved production incident remains.
