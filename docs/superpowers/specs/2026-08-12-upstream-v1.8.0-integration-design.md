# Upstream SUB/WAVE v1.8.0 Integration and Release Design

## Objective

Integrate the immutable upstream SUB/WAVE `v1.8.0` release into the fork as a true two-parent merge, preserve the fork's stricter and additive contracts, merge the reviewed result into `develop`, cut `v1.8.0-obiwave.1`, publish and scan the complete image matrix, and deploy the verified release to Ark.

## Immutable identities

- Fork base: `origin/develop` at `1013e38c69b920e74ec54d1ec477422e96f30389` when this design was approved.
- Upstream release: `v1.8.0` at `bc541fbecb6fe5ce5355cedb52a5cfcad965932f`.
- Shared merge base: upstream `v1.7.0` at `816fb6fd13d622988ad870e7b1ef55155ba314c2`.
- Intended fork release: `v1.8.0-obiwave.1`.
- Integration branch: `integrate/upstream-v1.8.0` in `.worktrees/integrate-upstream-v1.8.0`.

Before the merge, publish, PR merge, release cut, image deployment, or final verification, re-resolve the relevant remote identity and stop on drift. Never replace an existing tag or use a force push.

## Integration topology

The integration begins from the exact current `origin/develop` and merges the exact upstream tag commit with `--no-commit`. The resulting integration commit must have exactly two parents in this order:

1. the fork `develop` base;
2. `bc541fbecb6fe5ce5355cedb52a5cfcad965932f`.

The upstream tag must be an ancestor of the integration commit and the eventual merged `develop` commit. Cherry-picking or rebasing the upstream release is out of scope because either approach weakens release ancestry and makes future upstream merges harder to audit.

The first commit after conflict resolution is the topology-preserving integration commit. Any behavior corrections found by focused or full verification are separate, narrow follow-up commits so the merge itself remains inspectable.

## Upstream behavior to adopt

The composed fork must include all v1.8.0 behavior, including:

- speech/webhook events stamped at air time rather than controller handoff;
- station-level suppression of clock announcements;
- the armed next-transition label in the admin header;
- optional per-skill cron timers and their eligibility gates;
- requester-name speech;
- calibrated per-label audio moods and propagated energy;
- cloud TTS fallback targets that retain both engine and provider on both trigger paths;
- playlist reordering through dnd-kit with touch and keyboard support;
- schedule-booking confirmation;
- on-air/name persona ordering;
- the combined read-only debug state and DJ voice tree;
- usehooks-ts adoption and the controller dependency updates;
- the upstream CI image-push staggering intended to avoid GHCR rate limiting.

## Fork contracts to preserve

Upstream behavior is composed with, not substituted for, the fork's existing contracts. In particular, the integration must retain:

- provider-keyed search credentials and Kagi support;
- listener authentication, station-scoped stream credentials, and secret redaction;
- strict settings schemas, field-error ownership, generated schema mirrors, and request guards;
- station management, mounted-state behavior, stream-format hydration, and asynchronous request ownership;
- library TanStack Query cache behavior, liked/block/retag state, pagination, and stale-request guards;
- Liquidsoap metadata/voice timing, queue ownership, transition effects, idle policy, and archive behavior;
- skill scaffolding, config fields, context/tags, and operator-file preservation;
- analyzer, audio-mood, observatory, stem, and transition capabilities;
- portable CPU `subwave-tts-heavy` and Ark's default-on `subwave-tts-heavy-cuda` sidecar;
- strict CUDA Chatterbox execution, CPU-only PocketTTS, both-engine health, restart-free verification, and exact digest binding;
- historical recovery manifests and version-aware security policy;
- verifier dummy-backend provenance and the prohibition on production configuration, credentials, or service access during browserless testing;
- protected Portainer deployment, bounded deadlines, rollback reserve, exact repository-digest verification, and public stream probes.

## Conflict policy

For every overlapping path:

1. establish the upstream v1.8.0 contract from its implementation and tests;
2. establish the fork contract from its implementation, focused tests, and prior release/deployment contracts;
3. preserve upstream behavior;
4. preserve additive or stricter fork behavior;
5. compose both behaviors at the narrowest shared boundary;
6. add or update a focused test when the composition is not already executable;
7. stop for operator direction if the behaviors are genuinely incompatible.

No resolution may silently weaken authentication, secret isolation, verifier provenance, state-path containment, strict CUDA behavior, immutable artifact identity, vulnerability policy, deployment deadlines, or rollback.

Generated artifacts and dependency locks are regenerated from the composed source and manifests. They are not resolved by choosing one side wholesale or by hand-editing generated output.

## Verification architecture

### Baseline

The exact fork base receives locked installs and a full baseline before merge. The initial baseline for this design passed:

- controller lint and 573 tests;
- web lint, ten existing contract commands, and production build;
- MCP lint, CLI typecheck, and app lint/typecheck/contracts;
- 356 repository CI, release, security, and deployment tests.

Known warnings and package-audit notices are recorded but do not mask errors.

### Focused merge gates

Focused tests characterize both sides before conflict resolution and exercise the composed behavior afterward. Required focus areas are:

- speech air-time markers, voice events, requester names, clock policy, and next-transition labels;
- skill cron parsing, scheduling, eligibility, schemas, and preserved operator files;
- audio calibration, mood propagation, energy derivation, and tag-library persistence;
- cloud/local TTS fallback and provider ownership;
- debug state-tree containment and read-only exposure;
- playlist drag-and-drop, schedule confirmation, persona order, session feed, and hooks;
- settings/schema generation and dependency/lockfile coherence;
- image publication, scan matrices, historical recovery, CUDA TTS digest handoff, Portainer validation, deployment deadlines, and rollback.

Every discovered regression follows a captured failing test, minimal correction, passing focused rerun, and relevant broader rerun.

### Full gates

Before review and again after any material review correction, run:

- clean locked installs for root, controller, web, MCP, CLI, and app;
- schema/theme/assets generation with stable tracked mirrors;
- controller lint/typecheck and complete test suite;
- web lint, all contract commands, browserless forms/library/query plus upstream v1.8.0 verification scripts, and production build;
- MCP lint, CLI typecheck, app lint/typecheck/contracts;
- the complete CI/release/security/deployment Node contract suite;
- local Docker smoke builds for every publication flavor, including CPU and CUDA TTS;
- diff checks, conflict-marker scan, generated-artifact drift check, clean tracked status, and exact merge-parent proof.

Browser verification runs only against an isolated temporary state directory and task-local dummy Subsonic backend. The fail-closed provenance marker must be established before any browser verifier performs reads or writes. Production credentials, configuration, and services are never used for test setup.

## Review and merge

Maintain a conflict-resolution ledger for every non-trivial composition. The integration, focused corrections, and whole branch receive independent review. Critical or Important findings block progression and require a reviewed fix cycle followed by affected and full verification.

Publish the exact reviewed head to a ready-for-review PR targeting `develop`. Merge only when:

- base and head SHAs match the reviewed identities;
- the PR remains ready, clean, and mergeable;
- every required GitHub check succeeds;
- there are no requested changes or unresolved review threads.

Use a merge commit with an exact-head SHA guard. Verify the resulting `develop` commit contains the expected prior base and reviewed PR head as parents.

## Release and image publication

Before cutting the release, prove `v1.8.0-obiwave.1` and its GitHub release do not exist. Dispatch the checked-in fork-release workflow against the exact merged `develop` SHA. Verify the resulting tag and release target that SHA and that upstream v1.8.0 remains an ancestor.

The tag-triggered publish workflow must build its complete live matrix, including:

- portable CPU TTS;
- CUDA TTS for linux/amd64;
- lean, heavy, and CUDA analyzer variants;
- all other current release services and AIO variants.

The exact CUDA TTS digest produced by the build is passed through a strict same-run artifact to the digest-qualified scanner and protected deployment. The deploy verifies the running Ark container has exactly that repository digest. Mutable tags are never sufficient evidence.

All image scans must complete successfully. Aggregate policy must report zero unaccepted findings and zero invalid/orphaned acceptance records. New findings, unsupported pinned mirrors, or manifest drift stop normal progression. Recovery, if needed, is a separately reviewed immutable-artifact policy change; it may not rebuild, retag, bypass, or approve findings from the failed release run.

## Deployment and rollback

After policy succeeds, the protected Portainer job deploys the immutable release to Ark. It captures the prior stack before mutation and reserves sufficient time to restore and verify that snapshot within the workflow timeout.

Target verification requires:

- public health and a bounded decodable, non-silent MP3 stream sample;
- analyzer running and healthy on the exact release image;
- CUDA TTS running and healthy with zero restarts on the exact release tag and build digest;
- `/health` reporting both `chatterbox` and `pocket-tts`, both loaded, and `chatterbox_device` equal to `cuda`;
- PyTorch CUDA availability on Ark's NVIDIA RTX 2000 Ada Generation GPU;
- one successful disposable Chatterbox synthesis and one successful PocketTTS synthesis, both positive-duration valid WAV files and neither reporting fallback;
- removal of only those exact disposable WAV paths after evidence is captured;
- no CPU fallback in the CUDA Chatterbox startup or synthesis logs.

If target verification fails, restore and verify the exact prior stack. A successful rollback is reported as a failed deployment, not a successful release. A rollback failure is an incident and stops all further mutation.

No Portainer environment-variable change is expected for this integration. `HF_TOKEN` remains optional and only affects PocketTTS voice cloning; built-in PocketTTS voices must work without it.
