# v1.6.0-obiwave.1 Partial Publication Recovery Design

## Context and outcome

Release `v1.6.0-obiwave.1` was cut from merge commit
`87fd6e1398f2f8d204d7ed6c7d86ef2e6e2ed787`. A GitHub Actions outage
interrupted publication run `31117164489`. A successful partial attempt created
five immutable image tags, while five builds were cancelled. A later rerun
correctly failed the ordinary publication workflow's immutable-tag preflight.
GitHub now exposes a stale queued rerun with no jobs, and its force-cancel API
returns `409 Cannot cancel a workflow re-run that has not yet queued`.

The recovery will leave the original run and all attempts untouched, preserve
the five published digests, publish only the five absent images, seal the final
ten-image identity, scan every image by digest, apply the normal vulnerability
policy, and deploy the existing release only after all gates pass. It will not
recut the release, overwrite a tag, or use the ordinary publication workflow.

## Immutable invariants

- Git tag and GitHub release `v1.6.0-obiwave.1` remain at
  `87fd6e1398f2f8d204d7ed6c7d86ef2e6e2ed787`.
- Publication run `31117164489` is retained as outage and retry evidence.
- These existing tags must resolve to exactly their current repository digests:

  | Image | Required digest |
  |---|---|
  | `subwave-broadcast` | `sha256:a623e516992ade44d83ac72c231d2ecc278eb71c613d04212936a5ec03237c2f` |
  | `subwave-controller` | `sha256:fe765d8f9a491012c33c6828686cb350aa2e6f84acffd170fc038b4be93c614f` |
  | `subwave-aio` | `sha256:6d1c79424e19348653f929f0687582984d46fc964cdc388a49a03d58b8d3b1fe` |
  | `subwave-analyzer` | `sha256:4d4aaac6121f24699b3de79c00572afe87fd7c971b8b02c81c6bec12c7e1a1c9` |
  | `subwave-analyzer-cuda` | `sha256:cdf74b46d05a40d453b69541644b4e9e7c587617100a7484a616e358efd3c341` |

- These tags must be absent before recovery publishes them:
  `subwave-caddy`, `subwave-web`, `subwave-aio-heavy`,
  `subwave-tts-heavy`, and `subwave-analyzer-heavy`.
- No step may overwrite, retag, delete, or republish any existing release tag.
- All ten final images are scanned by repository digest, never by a mutable tag
  alone.
- Production deployment remains downstream of source/release validation, the
  full release gate, selective publication, sealed identity validation, and the
  aggregate vulnerability policy.

## Considered approaches

### Dedicated single-run recovery (selected)

A one-release manual workflow verifies the partial state, builds only the five
missing images, seals all ten digests into an artifact, scans those exact
digests, and deploys. This minimizes outage recovery time while keeping every
decision fail closed and every resulting digest auditable.

### Two-PR recovery

One workflow could publish the missing images and stop; a second PR could then
commit all ten known digests and reuse the existing scan/deploy recovery shape.
This gives a completely static pre-deployment manifest but creates a longer
unscanned interval and requires two reviewed merges and dispatches.

### Staging tags and registry copies

The missing images could first be built under staging tags, recorded in a
manifest, and copied to the final tags later. This adds a second tag namespace
and registry-copy semantics without improving the final immutable identity.

The dedicated single-run recovery is selected. Its runtime-generated portion is
not treated as free-form authority: the workflow itself fixes the source commit,
image set, build definitions, existing digests, scanner, and data flow from
Buildx outputs through sealing and scanning.

## Recovery identity contract

Add a checked-in v1.6 partial-recovery record under `security/releases/`. It
contains:

- release tag and source commit;
- pinned Trivy scanner identity;
- the five exact existing image digests;
- the five exact images permitted to be absent and built;
- the canonical ten-image order used by policy.

Extend `scripts/release/recovery-manifest.mjs` with commands that validate this
literal approved partial identity and support sealing. Checked-in JSON remains
data, not authority: the script holds the approved release identity and rejects
changes to the source, scanner, image names, order, existing digests, or missing
set.

The sealing command accepts registry observations only after publication. It
requires the five existing digests to remain unchanged, requires all five newly
built tags to exist with valid `sha256` repository digests, and emits a canonical
full recovery manifest containing all ten digests. The full manifest is uploaded
as a workflow artifact and included in the job summary for durable audit.

## Dedicated workflow

Create `.github/workflows/recover-v1.6.0-obiwave.1.yml` with manual dispatch
only and a release-specific, non-cancelling concurrency group distinct from
`publish-images-v1.6.0-obiwave.1`.

The jobs execute in this order:

1. **Validate partial state.** Check out the workflow revision containing the
   reviewed recovery controls,
   validate the partial manifest and scanner, verify the Git tag and public
   GitHub release both point to the source commit, verify the five existing
   remote digests, and prove the five build targets are absent.
2. **Run the normal release gate against the release source.** Add an optional
   checkout-ref input to the reusable CI workflow, defaulting to its present
   behavior for every existing caller. Recovery passes the literal source commit
   so lint, test, compose, generated-asset, and release checks execute against
   exactly `87fd6e13…`, not against the later recovery-control commit.
3. **Build missing images.** Use an explicit five-entry matrix copied from the
   ordinary publication workflow:

   | Image | Dockerfile | Platforms | Build arguments |
   |---|---|---|---|
   | `subwave-caddy` | `docker/Dockerfile.caddy` | `linux/amd64,linux/arm64` | none |
   | `subwave-web` | `web/Dockerfile` | `linux/amd64,linux/arm64` | none |
   | `subwave-aio-heavy` | `docker/Dockerfile.aio` | `linux/amd64` | `WITH_CLAP=1`, `WITH_DEMUCS=1` |
   | `subwave-tts-heavy` | `docker/Dockerfile.tts-heavy` | `linux/amd64` | none |
   | `subwave-analyzer-heavy` | `docker/Dockerfile.analyzer` | `linux/amd64` | `WITH_CLAP=1`, `WITH_DEMUCS=1` |

   Each matrix job checks out the literal release source commit, repeats its own
   absence check immediately before `buildx build --push`, stamps the OCI
   revision label with that source commit, and uploads the Buildx output digest
   as per-image evidence. Matrix fan-out is disabled until global validation and
   the release gate both succeed. The destination is only
   `ghcr.io/obiwancanoweme/<image>:v1.6.0-obiwave.1`, the canonical lowercase
   registry path already used by publication.
4. **Seal final identity.** Download the five per-image build-digest records and
   inspect all ten remote tags. Revalidate the five preserved digests and require
   every newly published registry digest to equal its corresponding Buildx
   output. Generate the canonical full manifest, validate it, upload it as
   `v1.6.0-obiwave.1-recovery-manifest`, and expose a base64-encoded copy only to
   the downstream scanner call.
5. **Scan and enforce policy.** Extend the reusable scan workflow with a
   mutually exclusive sealed-manifest input. It decodes and validates the
   manifest in each isolated scan job, verifies each remote tag still matches,
   pulls by tag-plus-digest, runs the pinned scanner, uploads JSON/SARIF, and
   applies the existing ten-image aggregate policy.
6. **Deploy.** Enter the protected `production` environment and invoke the
   existing Portainer release script only after validation, release gate, all
   five builds, sealing, and vulnerability policy succeed.

## Failure and rerun behavior

- If any expected existing digest differs, recovery stops before publication.
- If any expected-missing tag already exists, recovery stops rather than
  overwriting it.
- If a matrix attempt publishes some additional images and then fails, a blind
  rerun is expected to fail the initial absence check. Operators inspect the new
  partial state and update the reviewed recovery identity instead of bypassing
  immutability.
- If all builds publish but scanning or deployment fails, the sealed manifest
  artifact provides the exact identities for a follow-up no-build recovery.
- The stale outage run is not cancelled, deleted, or reused by this workflow.

## Security and permissions

- Workflow-level permissions are `contents: read`; only selective build jobs
  receive `packages: write`, scanners receive `packages: read` and
  `security-events: write`, and deployment receives no package-write authority.
- Registry login uses the scoped `GITHUB_TOKEN`; no long-lived registry secret is
  added.
- Release/source/scanner/image literals are not workflow-dispatch inputs.
- Recovery-control scripts come from the reviewed workflow revision, while CI
  and Docker build contexts come from a separate checkout pinned to the release
  source commit. The resulting images cannot accidentally include recovery-only
  commits.
- The sealed-manifest input is base64 only to survive GitHub output transport;
  it is decoded, schema-checked, release-checked, image-set-checked, and
  digest-checked before use.
- Shell interpolation never evaluates manifest content as code.

## Test and review strategy

Test-driven changes cover:

- exact partial-manifest acceptance and source/scanner/digest/missing-set
  tampering rejection;
- sealing only when preserved digests match and all ten canonical image digests
  are present;
- rejection of malformed, reordered, additional, or wrong-release sealed data;
- workflow identity, least-privilege permissions, separate concurrency,
  dependencies, exact five-image matrix, repeated absence checks, protected
  deployment, and absence of overwrite/retag/delete paths;
- sealed-manifest transport and digest-qualified scans in the reusable scanner;
- the v1.6 CUDA repository digest in release-aware vulnerability policy;
- unchanged v1.3 and v1.5 recovery behavior.

Focused release/security tests run first, followed by the repository's complete
release gate. A fresh branch review must report zero Critical and zero Important
findings before the PR is opened.

## Execution and completion

After the recovery PR merges, dispatch the dedicated workflow exactly once.
Completion requires:

- ten published tags with the five preserved digests unchanged;
- a retained sealed ten-image manifest artifact;
- ten successful digest-qualified scans and a passing aggregate policy;
- successful protected deployment of `v1.6.0-obiwave.1`;
- production health, now-playing, auth-routing, MP3 content-type, sample-size,
  and audio-level verification through the existing deployment checks;
- a follow-up commit of the sealed full manifest if durable repository-local
  audit, in addition to the workflow artifact, is desired.
