# Upstream SUB/WAVE v1.9.0 Integration and Release Design

Integrate immutable upstream SUB/WAVE `v1.9.0` into ObiWave as a true two-parent merge, preserve the fork's stricter and additive contracts, merge the reviewed result into `develop`, cut `v1.9.0-obiwave.1`, publish the complete image matrix, and deploy the release to production.

No iOS or Android EAS release is part of this integration.

## Conflict and semantic-merge policy

For every textual conflict and every high-risk auto-merged overlap:

1. establish the v1.9.0 contract from upstream implementation and tests;
2. establish the fork contract from implementation, tests, and prior release evidence;
3. preserve upstream behavior;
4. preserve additive or stricter fork behavior;
5. compose both at the narrowest owning boundary;
6. record the decision and executable proof in a task-local conflict ledger;
7. add or update a focused test when existing tests do not prove the composition;
8. stop for operator direction if the behaviors are genuinely incompatible.

Generated schemas, theme tokens, embedded CLI assets, and dependency lockfiles are regenerated from composed sources. They are never resolved by choosing one side wholesale or hand-editing generated content.

High-risk semantic audits include broadcast queue/timing, DJ-agent schemas and artist guards, skill abstention, analyzer backfill and embedding storage, library schema migration, era resolution, settings and listener buffering, Kokoro phonemization, Liquidsoap transitions/jingle gating, Docker startup, admin forms, show diagnostics, Observatory genres, generated schemas, release workflows, and deployment contracts.

## Verification architecture

### Baseline and focused gates

Before merging, install every locked dependency set and run the complete fork baseline. Characterize fork contracts and the new upstream behaviors at their existing v1.8 and v1.9 trees where useful. After composing the merge, run focused tests for every conflict and high-risk auto-merge.

Any discovered regression follows observed RED, minimal correction, focused GREEN, and broader rerun. Do not change passing behavior speculatively.

### Full gates

Before review and after every material correction, run:

- stable schema, theme-token, and embedded-asset generation;
- controller lint/typecheck and complete tests;
- web lint, declared contract tests, browserless verifiers, and production build;
- MCP lint, CLI typecheck, and native-app lint/typecheck/contracts;
- complete repository CI, release, security-library, and deployment contract suites;
- YAML validation, diff checks, conflict-marker scan, generated-artifact drift checks, and exact merge-parent proof;
- local Docker smoke builds for the publication matrix where host resources permit.

Admin/browser verification uses the repository `verify` skill with disposable state, spare ports, and a task-local dummy Subsonic backend. Production configuration, credentials, state, and services are prohibited during test setup.

## Review and merge

Independently review the integration commit, follow-up corrections, and final branch. Critical or Important findings block progression and require a focused fix, affected test rerun, and renewed review.

Push the exact reviewed head to a ready-for-review PR targeting `develop`. Merge only when base and head SHAs match the reviewed identities, required checks pass, the PR is mergeable, and no requested changes or unresolved review threads remain. Use a merge commit with an exact-head guard, then prove the expected ancestry on remote `develop`.

## Release and image publication

Before release, prove `v1.9.0-obiwave.1` and its GitHub release are absent. Dispatch `.github/workflows/cut-fork-release.yml` with version `1.9.0`, revision `1`, and the exact merged `develop` SHA. Verify the immutable tag and GitHub release target that SHA and retain upstream `v1.9.0` ancestry.

The tag-triggered publication workflow builds and pushes the complete fork matrix, including portable CPU TTS, CUDA TTS, lean/heavy/CUDA analyzer variants, service images, and AIO variants. The exact CUDA TTS digest artifact flows directly from build to deployment.

The manual-only scanning policy is a release invariant. Do not invoke `scan-images.yml`, add a scan dependency, or restore any scheduled/reusable trigger during integration or release.

## Deployment and rollback

The protected Portainer job deploys the immutable release after its build, mirror, and release gates. It captures the prior stack before mutation and reserves enough time to restore and verify that snapshot within the workflow timeout.

Target verification requires:

- public health and a bounded decodable, non-silent MP3 sample;
- exact release image identities for the running stack;
- analyzer health on the intended lean/heavy/CUDA flavor;
- CUDA TTS health with zero restarts and CUDA runtime attestation;
- both Chatterbox and PocketTTS loaded;
- one valid positive-duration disposable synthesis from each engine, with no fallback;
- removal of only the exact disposable probe files;
- no CPU fallback in CUDA startup or synthesis logs.

If target verification fails, restore and verify the exact prior stack. A successful rollback still means the deployment failed. A rollback failure is an incident and stops all further mutation.

## Evidence and completion

Task-local ignored evidence records identities, conflict resolutions, tests, reviews, PR/merge state, release/tag state, image digests, deployment target and prior version, health/audio/GPU/TTS probes, rollback evidence, warnings, cleanup, and unresolved concerns.

Completion requires:

- an exact two-parent v1.9.0 integration merged into `develop`;
- all required verification and review gates passing;
- immutable `v1.9.0-obiwave.1` published from the merged SHA;
- automatic vulnerability scanning still absent and manual scanning still available;
- production running the target release with verified health, audio, analyzer, image identity, CUDA TTS, and PocketTTS;
- disposable probes removed and the tracked integration worktree clean.
