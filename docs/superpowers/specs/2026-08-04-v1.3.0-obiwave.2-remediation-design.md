# v1.3.0-obiwave.2 Audit Remediation Design

## Goal

Remediate every Important and Minor finding from the final
`v1.3.0-obiwave.1` whole-release audit, make container vulnerability scanning
deployment-gating, merge the reviewed changes into `develop`, and publish and
deploy the immutable follow-up release `v1.3.0-obiwave.2`.

The deployed `.1` tag, GitHub release, images, and production state remain
immutable. The `.2` release starts from exact fork commit:

```text
6005f8e3f98a5266513c2d0a5dae104d361f04e5
```

Upstream SUB/WAVE `v1.4.0` integration is explicitly deferred until `.2` is
complete. No upstream v1.4 code is included in this remediation.

## Release Scope

The release contains one cohesive audit-remediation change set:

- close the listener-auth trailing-slash and subpath edge bypass;
- make archive-root enumeration failures visible to the scheduler and Admin;
- enforce no-clobber semantics for concurrent same-name voice imports;
- isolate LiteLLM onboarding URL, model, and credentials from other providers;
- make analyzer readiness and restart state deployment-gating;
- fix liked-library pagination, stale-response, desktop-action, trim-priority,
  and block-state reconciliation defects;
- clear the compatibility TTS password input after successful persistence;
- scan all ten published images;
- patch actionable Critical and High vulnerabilities;
- record justified, owned, expiring exceptions for remaining Critical or High
  vulnerabilities that have no usable fix or are unreachable; and
- block publication and deployment on any unaccepted, expired, or malformed
  Critical or High finding.

No unrelated feature work, UI redesign, dependency modernization, or v1.4
integration belongs in `.2`.

## Git and Isolation

All work occurs in the linked worktree:

```text
.worktrees/remediate-v1.3.0-obiwave.2
```

on branch:

```text
remediate/v1.3.0-obiwave.2
```

The primary checkout is stale and contains unrelated untracked planning files.
It is not updated, cleaned, stashed, or modified.

The remediation is proposed through a pull request into `develop`. The PR is
merged with a merge commit only after its exact reviewed head passes every
required check. The release tag is cut from that merge commit; no history is
rewritten and `.1` is never moved or overwritten.

## Edge Isolation

Both `docker/Caddyfile` and `docker/aio/Caddyfile` must block the complete
internal listener-auth namespace before requests reach Express:

```text
/api/listener-auth
/api/listener-auth/
/api/listener-auth/*
```

The matcher must not block neighboring public routes. Edge contract tests must
exercise exact, trailing-slash, nested, encoded-path, method, and adjacent-path
cases for both Caddy deployment shapes. The production verification must prove
the exact and trailing-slash forms return the edge 404 even if listener auth is
disabled in current Ark settings.

## Archive Cleanup Failure Semantics

Archive retention and clear-all operations must distinguish three outcomes:

1. successful deletion;
2. per-day deletion failure; and
3. failure to enumerate the archive root.

Root enumeration errors must not be converted to an empty success. The archive
module exposes a sanitized typed failure that preserves the operation and
cause for internal logging without leaking host paths to Admin clients.

The scheduler logs root-scan and per-day failures as failed retention work. The
Admin clear route returns a non-200 response with `ok: false`, successful
partial totals when applicable, and sanitized failure details. Missing archive
roots remain a successful empty state when the filesystem reports `ENOENT`;
permission, I/O, and unexpected errors are failures.

## Atomic Voice Import

Voice import continues to transcode into a hidden same-filesystem temporary
sibling and clean it on every failure. Promotion to the canonical filename is
non-replacing:

- atomically link or otherwise claim the canonical destination;
- return the existing duplicate-name contract on `EEXIST`;
- unlink the temporary file after successful promotion; and
- never expose partial or hidden files through voice discovery.

Two concurrent imports for the same normalized name must produce exactly one
success and one duplicate result. The loser must not overwrite or remove the
winner.

## Provider-Scoped Onboarding State

Onboarding keeps independent drafts for provider-specific URL, model, and key
fields. Switching providers restores that provider's draft or its documented
default; it never reinterprets another provider's custom endpoint as a LiteLLM
endpoint.

At minimum, the provider transition contract covers:

- `openai-compatible` with a non-empty custom base URL to LiteLLM;
- LiteLLM back to `openai-compatible`;
- stale asynchronous model-discovery results after a provider change; and
- serialization of only the currently selected provider's fields.

A LiteLLM bearer must never be sent to a previously selected provider host.
Existing provider-owned key redaction and environment fallback behavior remain
unchanged.

## Analyzer Deployment Gate

The analyzer service gains a readiness-oriented health check based on its
existing `/health` endpoint. The check must work for lean, heavy, CUDA, and AIO
deployment shapes without requiring optional model residency.

Production deployment verification must fail unless the Portainer-observed
analyzer container:

- is running;
- uses the exact release image tag;
- reports healthy/readiness success;
- has zero unexpected restarts; and
- answers the analyzer health contract.

Controller health and MP3 byte flow remain required but are not substitutes
for analyzer verification. A failed analyzer gate invokes the existing
verified rollback path; it must never be reported as a successful deployment.

## Library and Likes Correctness

The Admin library must maintain a usable, truthful view while mutations and
requests overlap:

- clamp or reset the page when totals, sort order, or library mode change;
- return from an emptied last page to the newest valid page;
- associate fetches with a generation and ignore stale offset/sort responses;
- expose clear-all likes through an accessible desktop action as well as the
  mobile menu;
- reconcile block status for liked rows after never-play mutations; and
- preserve the newest operator-curated likes ahead of listener likes when the
  persisted record cap is reached.

Operator records are never evicted in favor of listener records when operator
records alone fill the cap. Existing ordering among retained operator records
remains newest-first according to the store's established timestamp semantics.

## Compatibility TTS Secret State

After the controller confirms that a compatibility API key was persisted, the
Admin TTS form clears `compatKeyInput` and any equivalent raw password state.
The UI continues to display only the redacted saved-key sentinel. Failed saves
retain the input so the operator can retry. Provider switching must not copy
the raw compatibility key into another provider field.

## Vulnerability Policy

### Complete image coverage

The release scan matrix covers every published image:

```text
subwave-caddy
subwave-broadcast
subwave-controller
subwave-web
subwave-aio
subwave-aio-heavy
subwave-tts-heavy
subwave-analyzer
subwave-analyzer-heavy
subwave-analyzer-cuda
```

The scan operates on the exact immutable release tag, not `latest` or a local
build alias. CUDA remains an exact upstream manifest mirror; its accepted-risk
records may differ from fork-built images because the fork cannot patch it
without breaking digest equality.

### Actionable findings

Critical and High findings are grouped by unique vulnerability, package,
installed version, fixed version, image, and platform. The remediation updates
base images or dependencies when a compatible fixed version exists and the
change can be verified without expanding product scope.

Raw alert counts are not treated as distinct vulnerabilities: duplicate image,
platform, and layer occurrences are consolidated for triage, but every
occurrence remains covered by either a fix or an explicit exception.

### Accepted-risk manifest

Remaining Critical or High findings require a version-controlled manifest with
one record per accepted vulnerability scope. Each record contains:

- vulnerability identifier;
- affected image or exact image set;
- affected package and installed version constraint;
- disposition: `no-fix`, `unreachable`, or `upstream-mirror`;
- concrete justification tied to how the image runs;
- owner;
- approval date;
- expiry date; and
- optional upstream tracking reference.

Exceptions are narrow: an identifier-only global ignore is invalid. Expiry may
not exceed 90 days from approval. The validation tool rejects duplicates,
unknown images, missing fields, invalid dates, already expired entries, and
exceptions that do not match a current finding.

### Gating behavior

Trivy still uploads SARIF with `if: always()` for observability, but a separate
machine-readable JSON result is evaluated before deployment. The gate fails on:

- any unaccepted Critical or High occurrence;
- any expired or malformed exception;
- an exception whose image/package/version scope does not match;
- an expected image missing from the scan matrix;
- an unreadable or incomplete scan result; or
- a scanner execution failure.

The release workflow may deploy only after all ten image scans and the
aggregate acceptance gate succeed. Scheduled scans use the same policy and
surface failures without mutating or republishing an existing tag.

## Verification

Every behavior change uses red/green test-driven development. Focused tests
must first fail for the audited defect, then pass after the minimal fix.

Required focused coverage includes:

- listener-auth exact, slash, nested, encoded, method, and adjacent paths in
  both Caddy configurations;
- archive-root `ENOENT`, permission/I/O failure, per-day failure, and partial
  success for prune and clear;
- concurrent same-name voice imports, duplicate error, atomic promotion, and
  temporary-file cleanup;
- non-empty cross-provider onboarding URLs, model drafts, keys, and stale
  async responses;
- analyzer healthy, unhealthy, restarting, wrong-tag, and missing states in
  Compose and Portainer verification;
- liked-library page clamp, sort/mode generation races, desktop clear-all,
  block reconciliation, and operator-priority trim behavior;
- compatibility-key success clearing and failure retention;
- accepted-risk schema, expiry, scope matching, orphan detection, full image
  coverage, scan failure, and unaccepted-finding rejection; and
- release-workflow ordering that makes the vulnerability gate a dependency of
  production deployment.

Before PR creation, run the complete controller, web, native app, CLI, MCP,
generated-asset, production-build, image-policy, and deployment-contract
matrices. Web and app warning counts must not exceed the established ceilings
of seven and four. No gate may be weakened to make the matrix pass.

The PR receives an independent code and security review. Every Critical and
Important finding is resolved and re-reviewed before merge. GitHub Actions must
pass on the exact reviewed head.

## Release and Production Verification

The follow-up tag is exactly:

```text
v1.3.0-obiwave.2
```

Preflight fails closed if the Git tag, GitHub release, or any of the ten GHCR
tags already exists. The release is cut only from the reviewed `develop` merge
SHA and only while exact upstream `v1.3.0` remains an ancestor.

The tag-triggered workflow performs one immutable publication attempt. It
validates the tag, repeats the complete quality gate, proves destination-tag
absence, mirrors CUDA with digest equality, publishes nine fork-built images,
scans and gates all ten images, deploys through protected Portainer, and uses
verified rollback on deployment failure.

After success, independent probes verify:

- all ten manifests and expected platforms;
- CUDA source/destination digest equality;
- exact tagged images on Ark;
- analyzer, controller, and broadcast health;
- zero unexpected restart counts;
- clean recent logs;
- public `on-air` health and populated now-playing metadata;
- exact and slash listener-auth edge isolation;
- 65,536 MP3 range bytes with `audio/mpeg`; and
- audible audio above the `-50 dB` silence threshold.

Temporary probe files are deleted by exact path. No tag recreation, image
overwrite, destructive stack operation, blind workflow rerun, or modification
of `.1` is permitted.

## Failure Policy

- An ambiguous security disposition blocks the release until reviewed.
- An actionable Critical or High finding without a patch blocks `.2`.
- An unaccepted, malformed, over-broad, or expired exception blocks `.2`.
- A behavior regression, warning increase, failed build, or generated drift
  blocks the PR.
- A failed publication job stops without recreating the tag.
- A deployment-only failure is diagnosed before any narrowly scoped retry.
- A live-service failure invokes the existing verified rollback path.
- Any remediation that requires upstream v1.4 code is deferred to the later
  v1.4 integration unless it is the only safe fix for an audited vulnerability;
  that exception requires explicit user approval.
