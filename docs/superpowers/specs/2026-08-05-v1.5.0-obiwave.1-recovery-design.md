# v1.5.0-obiwave.1 CUDA Policy Recovery Design

## Context and outcome

Release `v1.5.0-obiwave.1` was cut from merge commit `fe269a1e632fe6f886ac987f641f41326e1392e0`. Publication run `31063266344` successfully created all ten immutable image tags and completed all ten Trivy scans, then stopped before deployment at the aggregate vulnerability-policy gate.

The failure was not an unaccepted vulnerability. The replay found 932 HIGH/CRITICAL findings, 932 accepted findings, and zero unaccepted findings. The sole violation was a CUDA repository-digest mismatch: policy still pinned upstream v1.3 digest `sha256:c6964797b8a88dd2fa9291778543c27594350aba84c7c2f2d25560cd5150bb72`, while the exact upstream and mirrored v1.5 index is `sha256:a69d2f866eb9d991a69212b5605c15a3631d4d21cec8c4608a6cb29f9d7c9cc2`.

The recovery will make CUDA policy release-aware, preserve the existing v1.3 recovery contract, add a fail-closed v1.5 recovery manifest and manual workflow, rescan the already-published digest-qualified images, and deploy those exact images. It will not rebuild, republish, retag, overwrite, or create `v1.5.0-obiwave.2`.

## Immutable invariants

- `v1.5.0-obiwave.1` remains at `fe269a1e632fe6f886ac987f641f41326e1392e0`.
- All ten existing `v1.5.0-obiwave.1` image tags remain byte-for-byte unchanged.
- The v1.3 recovery remains valid: `v1.3.0-obiwave.2` continues to require CUDA digest `c6964797…`.
- The v1.5 recovery requires CUDA digest `a69d2f86…` and the nine other exact published digests listed below.
- Unknown release tags or tag/digest pairings fail closed.
- Recovery performs no build, push, registry retag, release creation, or acceptance bypass.
- Production deployment remains downstream of immutable-artifact validation and the full aggregate vulnerability policy.

## Release-aware CUDA policy

`scripts/security/trivy-policy.mjs` will replace its single global CUDA digest with an explicit immutable map:

- `v1.3.0-obiwave.2` → `sha256:c6964797b8a88dd2fa9291778543c27594350aba84c7c2f2d25560cd5150bb72`
- `v1.5.0-obiwave.1` → `sha256:a69d2f866eb9d991a69212b5605c15a3631d4d21cec8c4608a6cb29f9d7c9cc2`

The policy selects the expected digest from the release tag it already validates. A supported tag with the other release's digest fails. An unsupported tag fails with a dedicated policy violation rather than silently omitting the CUDA identity check.

This keeps historical recovery reproducible and prevents a future release from inheriting a stale digest unnoticed.

## Acceptance record review

The 160 `upstream-mirror` records scoped to `subwave-analyzer-cuda` still match the v1.5 scan by vulnerability, image, package, and installed version. Their current justification is nevertheless false for v1.5 because it claims the v1.3 digest is universal.

Those 160 records will retain their finding scope, disposition, owner, tracking URL, and risk decision. Their justification will state that the image is an exact immutable upstream mirror and that the checked-in release-aware policy binds each supported release to its reviewed repository digest. Because this is a fresh human review, their approval window will become `approvedOn: 2026-08-05` and `expiresOn: 2026-11-03`.

No `no-fix` or `unreachable` record changes, and no new CVE acceptance is introduced.

## Recovery workflow

Create `.github/workflows/recover-v1.5.0-obiwave.1.yml` by following the proven v1.3 recovery shape with v1.5 literals:

1. Manual dispatch only, with non-cancelling release-specific concurrency.
2. Validate the release tag, public GitHub release, source commit, pinned scanner, and all ten remote image digests.
3. Call `scan-images.yml` with the v1.5 recovery manifest. Each scanner verifies the canonical tag digest, pulls by tag-plus-digest, creates only a runner-local tag for Trivy identity, rescans, and re-verifies the remote digest.
4. Run aggregate policy with the release-aware CUDA digest and reviewed acceptance file.
5. Enter the protected `production` environment only after validation and policy both succeed.
6. Deploy `v1.5.0-obiwave.1` through the existing Portainer release script.

The workflow contains no build or publication command. It is dispatched once after its PR is merged and all checks are green; failures stop without automatic rerun.
